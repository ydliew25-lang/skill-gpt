# 搭建试吃活动数据平台

让品牌能决定改什么商品，让零售方能决定下一场怎么安排，让内部人员能判断哪条证据可以发布。以一条实际可走通的路径串起交付物：从当前角色的总览点进专题，从专题找到对应顾客原话，再下载同范围的数据。

## 1. 先确定交付阶段和角色决策

先读已有页面、流程图、权限表、视觉规范和本次反馈。用户要求「先出方案，确认后行动」时，交付信息架构、角色权限和一条可走查的路径，等用户确认。已经授权制作或修改时，直接在已有平台实现；对单点改版，保留其他正常入口和已有数据。

| 角色 | 优先回答 | 页面上应能采取的动作 |
|---|---|---|
| 品牌方 | 试吃如何执行？该改配方、包装还是售前介绍？哪些人因什么场景表现出兴趣？ | 按授权商品和门店查看已发布结论、原话和报告，选择下一场验证项 |
| 零售方 | 本店承担哪些成本？哪些时段要补样？通行或设备异常是否影响参与？ | 对照本店时段、点位和记录调整活动，下载本店运营报告 |
| 内部人员 | 哪些指代或标签待核？发布修订会影响哪个门店、哪些报告？ | 在项目授权范围内复核、修订、预览、发布和下载源文件 |

为高优先问题各写一行「要做的决定／需要的证据／指标单位和分母／可查看的人／页面与下载入口」。门店销售、全店客流、ROI 等问题需对照交易、计数或费用资料；缺数据时列明还需补哪项。

## 2. 按门店和场次配对来源

给每场建立资料清单，记录门店、场次、商品、日期与时区、原始日志、标注工作簿、对应报告、标注规范版本、真实或模拟属性。区分「同一活动的修订版」与「不同门店的独立场次」；若对应关系未明且会改变汇总，先核对。门店实名缺失时采用可追溯的临时名称，并说明对应关系。

清点表头与数据内容。原始事件、逐句标注、咨询事项、指标计数成员、图像复核记录分别保存。保留原文、工作表、行号或事件号，以「门店＋场次＋源编号」关联；同一句话可对应多项标注。合并新店时，分别保留历史数据、规则版本和各店草稿。可用随包的 [来源清点脚本](scripts/inventory_sources.py) 核对文件和工作表。

在技能目录运行 `python3 scripts/inventory_sources.py <门店资料目录> <规则文件>`。需要读 XLSX 时使用装有 openpyxl 的 Python。将 JSON 清单存到输入目录外；检查错误列表，再把工作表非空行数扣除实际表头和说明行，与导入条数核对。业务上的拨数、人次和份数另按指标卡计算。

## 3. 先写统计口径，再生成结论

按 [指标与证据模板](references/metrics-and-evidence.md) 定义分子、分母、去重键、范围、缺失处理和可回查的成员。用本店原始记录复算报告中的关键数字，遇到冲突保留双方来源、差异和待核状态。

分开记录顾客的询问、索样、领样、确认品尝、体验评价、购买意向和付款。在全部接触者中分析兴趣，或在确认品尝者中分析兴趣，均须把人群范围和单位写在结论旁。市场定位先写具体分布，如独居、与家人同住、未知各几人；把独自到台、结伴到台另列为同行形态。把「谁对什么感兴趣、为什么、打算怎样买」写成可读内容。

碰到「这个、那个」时，按时间戳定位原句和相关画面，用视觉证据核对所指商品。仅补充证据支持的词，核查对象、原意与完整性。保留原句、最小补全句、时间片段及复核状态；证据不足的关键项标「待与图像确认」进入人工队列。缺画面时保留未知。复核通过并发布后，再按同一统计口径使用；一般项若排除，留存原因。

## 4. 把结论、依据和标注做成连续交互

- **总览**放在顶部主导航的第一项。上方「本场核心结论」每个业务板块取一条最重要发现，注明单位及基数，整卡可点击。下方「本场其他结论」给有依据的研发、运营或复核建议。原话和大表留在详情。
- **专题**沿用顶部标签，左上给结论、左下按支持力排列依据、右侧放对应数据表。品牌方依次提供运营情况、用户反馈、市场定位；市场定位中优先呈现兴趣人群画像，再呈现兴趣信号、购买任务与原因。
- **图形**优先用饼图表达同一总体里互斥、可加总的占比，并同时显示分子、分母、百分比和单位。单值、单一类别或仅有两个等量类别用文字。多选信号分项列数并说明可重叠。
- **标注数据集**设独立入口。左侧点父主题，如「价格与购买」，右侧显示该主题全集；点叶维度，如「价格」，只呈现该维度结论及匹配的明细。专题分支、右侧表、CSV 共用筛选；返回上级时恢复角色、门店、时段、维度和滚动位置。
- **外观与辅助入口**采用项目提供的品牌颜色、字体和标志。左侧保留账号和全局筛选。需要复用灵美交互时，点头像或账号文字打开资料，点「···」打开最小化或退出。帮助打开常见问题，左下保留「联系我们」；缺联系方式时显示待配置。

## 5. 接入数据、权限、发布与下载

在页面和报表生成之前统一应用账号、授权商品／门店、场次、时段和发布状态。将表格、计数、图表、下钻和导出接到同一套筛选逻辑。一个指标取不到数据时，显示原因及可用证据。旧演示样本与新导入场次单独标识。

内部修订按店、场次和版本保存。保留源文件、修订记录、草稿和已发布快照。对外提供已发布视图；原始报告按导入版次显示，动态摘要注明当前口径。若交付为生产平台，服务端查询与文件下载均校验授权；在演示原型中明确账号切换与本地保存的性质。

「分析报告下载」和「数据集下载」均先打开面板。显示当前门店、时段、维度、条数与格式，再由用户选取文件。品牌方和零售方下载授权范围的标注 CSV 和角色报告；内部另可下载本店整场标注工作簿、原始日志和项目共用的标注与分析体系。给整场原件和当前筛选导出分别标范围；0 条时说明原因。

## 6. 走查后交付

按 [交互验收表](references/acceptance.md) 用实际入口验证各角色、门店与时段。至少完整走一条「总览 → 专题 → 叶维度 → 原话 → 导出」路径并比对下载内容，另外走一次内部复核、保存和发布。交付时说明入口、已验证范围、模拟数据或临时店名等假设，以及仍待补充的资料。发布中的版本按实际状态描述。
